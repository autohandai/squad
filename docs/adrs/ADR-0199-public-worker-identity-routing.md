# ADR-0199: Route hosted identity checks through the public Worker endpoint

Date: 2026-11-12
Status: Implemented; isolated hosted verification

## Context and evidence

The owned API verifies sign-in with `fetch(IDENTITY_ORIGIN + '/v1/profile')`
and current team access with `/v1/accounts`. Its local Miniflare tests use an
explicit `outboundService`, which does not reproduce public Worker routing.
The deployment configuration did not set `global_fetch_strictly_public`.

An isolated Cloudflare deployment of PR #61 source `bb3132b` used a synthetic
identity Worker, a new D1 database with both migrations, and two new private R2
buckets. Direct identity profile retrieval and both health endpoints returned
200, but exchanging that same identity through the API returned 503
`identity_rejected`. The asserting probe reproduced the failure before any
configuration change. No real account credentials or production resources
participated.

Changing only the API's compatibility flags to include
`global_fetch_strictly_public` made the same exchange return 201. The baseline
Worker version was `464067fb-6d2c-4a51-953e-b88be2997d68`; the flag-only version
was `e34217af-c95c-4a73-80ea-920c51d153f8`. The evidence is the isolated run's
`auth-red.json` and `auth-green.json` in
`.codex-artifacts/ownership/hosted-proof/`, generated by `probe.mjs`.

Cloudflare documents that Worker-to-Worker fetch requires a service binding
or this flag, and that without the flag requests within the Worker's zone can
bypass Workers and reach the zone's origin instead. The observed flag-only
comparison, rather than a guessed upstream outage, establishes the fix.
Sources: [Fetch](https://developers.cloudflare.com/workers/runtime-apis/fetch/)
and [compatibility flags](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#global-fetch-strictly-public).

## Decision

Enable `global_fetch_strictly_public` explicitly in the production Squad API
configuration. Keep the existing HTTPS identity origin, redirect refusal,
timeouts, immutable subject validation and per-operation membership checks.
This preserves the deployment's public identity-service contract without
coupling Squad to an account-specific service binding.

## Consequences

- Identity checks follow the public endpoint and its Cloudflare security
  rules. An unavailable or rejected identity still fails closed.
- Public network routing adds a dependency on the public identity endpoint;
  a private service binding remains a possible future deployment choice.
- Local outbound-service fixtures alone cannot prove hosted identity wiring.
  The remote probe supplies that evidence. It is not a claim that PR #61 was
  merged, deployed to production or published in an installer.
- This change does not automatically create hosted-test resources in CI or
  introduce fixture credentials into the product. Hosted proofs require
  explicitly isolated resources and cleanup.
