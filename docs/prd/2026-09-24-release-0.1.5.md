# PRD: Autohand Squad 0.1.5 — first conversation onboarding, fluid presence, squad recruiting

Status: accepted for implementation
Date: 2026-09-24
Owner: Igor Costa
Scope: `autohandSWE` web app, Node bridge, desktop shell. Ships as release 0.1.5.

## 1. Problem

1. **Onboarding reads like a diagnostics report.** The first-run page lists
   five checks (runtime, account, provider, workspace, member) with badges and
   paths. Four of five are already green for most installs, so the page asks
   people to read status they cannot act on, and it ends on a directory, not
   on the thing they installed the app for: talking to a teammate about their
   code.
2. **Channel replies feel mechanical.** When a channel has four members, four
   identical "X is typing…" rows appear the instant the user sends, each with
   a spinner, plus a fixed "Eva: Working ●" footer. Nothing changes until the
   full reply lands, so the room feels like a queue, not people responding.
3. **The squad does not come to the work.** A channel can point at project
   folders, and members have roles and skills, but nothing connects them. A
   user who adds a Rust workspace to a channel with only a frontend developer
   gets no hint that the DevOps or backend teammate should be there.
4. **Long agent turns die.** A member that runs tools for more than the chat
   timeout is cut off with "chat timed out waiting for Autohand SDK" even
   though it is actively working (78 steps, 26 tool calls in the reported
   case). The timeout is absolute rather than inactivity based.
5. **Two cosmetic gaps:** the collapsed sidebar rail's icon does not match the
   expanded header's icon.

## 2. Goals

- A new user reaches a real first conversation with a teammate on their own
  folder within two minutes of signing in, with no setup vocabulary.
- Channel presence reads as people: one living line that names who is
  thinking, who is typing, and who is running tools, and replies that appear
  when they start rather than as placeholders.
- Squad recruiting: when a channel gains a project folder, members whose role
  matches what the folder needs, and whom no current member covers, ask to
  join. The user alone sees the request and accepts or dismisses it. On by
  default; one switch in Settings → Chat turns it off.
- A working member is never cut off while it is producing events.

## 3. Non-goals

- Marketing or tour screens. Onboarding stays a native app view.
- Automatic membership changes. Recruiting proposes; the user decides.
- New setup systems. Onboarding reuses the account gate, native folder
  picker, member creation, and member chat that already exist.
- Provider configuration in onboarding. Autohand AI works with the account;
  other providers stay in Settings.

## 4. Users and scenarios

- **New developer, first run.** Signs in, points at `~/code/shop`, meets
  "Noah, Frontend developer" suggested from the Vite/React markers, renames
  him or picks another role, and lands in a chat whose first message is
  already drafted: "Walk me through this repo and tell me what you'd tackle
  first." Sends it. Done.
- **Team lead adding a project to a channel.** Adds `~/code/api` (Rust +
  Docker) to `#client-abc`, whose only member is a frontend developer. A quiet
  notice appears in the channel, visible only to the lead: "Kai wants to join
  #client-abc — DevOps engineer. He can help with the Dockerfile and CI in
  `api`; nobody in the channel covers that." Buttons: Add Kai · Not now.
- **Anyone in a busy channel.** Sends "is anyone working on something?" to a
  four-member channel. A line under the composer reads "Iris, Noah and 2
  others are thinking…" with moving dots; as each starts writing, its message
  appears and streams. No empty rows.

## 5. Requirements

### 5.1 Onboarding (first conversation)

- R1. Route `/welcome` shows one column, three moments, no checklist:
  **Point at a folder** → **Meet your first teammate** → **Start talking**.
  Progress is the moment you are in; there is no percentage bar.
- R2. Runtime, account, and provider are silent when ready. When one is not,
  it appears as one inline sentence with one action (Sign in, Open provider
  settings, Retry) above the current moment. Sign-in remains the account
  gate's job.
- R3. Folder: native picker (`POST /api/workspaces/pick`) plus the recent
  workspaces the bridge already lists. After a choice, the bridge profiles the
  folder (`POST /api/workspaces/profile`) and the page shows one sentence:
  "A React and TypeScript app with tests and a Dockerfile."
- R4. Teammate: three role suggestions ranked from the profile (see 5.3), the
  top one preselected, a name field prefilled from the role's default name.
  "Create someone else" opens the existing member creation route with the
  folder preset.
- R5. Start talking: creates the member through the existing member creation
  path, marks onboarding complete, and opens that member's chat with a
  drafted first message the user can edit before sending.
- R6. Skip remains available once signed in and lands on the directory, as
  today. Completed or skipped state persists as before.

### 5.2 Fluid presence in channels

- R7. Placeholder rows are not rendered while a reply has no body. A reply
  appears in the stream when its first text arrives and streams from there.
- R8. One presence line replaces the per-member "Working" footer. It groups
  members by state: thinking (no output yet), typing (text streaming),
  running tools (last event was a tool). Copy: "Iris is thinking…",
  "Iris and Noah are typing…", "Iris, Noah and 2 others are thinking…".
  Avatars stack in front of the text; three dots animate.
- R9. The line renders nothing when nobody is active, and updates without
  layout shift.

### 5.3 Squad recruiting

- R10. Folder profile (bridge): languages, frameworks, and needs detected
  from markers and file extensions: frontend, backend, mobile, infra/CI,
  tests, docs, data, security. Cheap: top two levels plus marker files, no
  content parsing beyond `package.json` dependencies.
- R11. Matching (web, pure function): each role template declares the needs it
  serves. A member is proposed when the channel's projects raise a need that
  none of the channel's members serve and the member serves it. Rank by needs
  served; propose at most two members per channel per profile.
- R12. Proposals render as a notice in the channel stream, addressed to the
  user only: never sent to members, never part of teammate context, never
  exported. Actions: Add (adds the member to the channel) and Not now
  (dismisses that member for that project profile).
- R13. Trigger: when a channel's projects change and when a channel opens
  with projects and no computed proposals for that profile.
- R14. Setting `Settings → Chat → Squad suggestions`, on by default.

### 5.4 Long turns

- R15. The chat timeout becomes an inactivity window: it resets on every SDK
  event. A hard ceiling of 45 minutes still ends a runaway turn. The error
  names the cause: "No activity from Autohand Code for 5 minutes."

### 5.5 Sidebar icon

- R16. Collapsed rail and expanded header use the same panel icon family at
  the same size, so the two toggles look like one control.

## 6. Success criteria

- Fresh profile to first sent message: three clicks and one text field.
- No "is typing…" placeholder rows in channels; presence line copy matches R8.
- Adding a Rust + Docker project to a frontend-only channel proposes the
  DevOps member; adding a React project to that channel proposes nothing.
- A member running tools for eight minutes completes without timing out.

## 7. Release

Version 0.1.5, stable channel, from `main` after this branch merges. The
CHANGELOG's Unreleased entries move under 0.1.5.
